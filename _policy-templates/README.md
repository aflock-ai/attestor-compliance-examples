# Multi-step policy templates

Every example in this repo is **validated end-to-end** — running cilock + getting an envelope isn't enough. The example must also include a multi-step **cilock verify** run against a policy that gates on the scanner's actual findings. That's what cilock adds on top of the bare tool output.

This directory holds the reusable pieces:

- [`policy-shape.md`](./policy-shape.md) — the structure of a `policy.json`, with annotations explaining every field
- [`rego-snippets/`](./rego-snippets/) — drop-in Rego policies for common gates (no-Critical-CVEs, must-be-from-this-repo, etc.) decoded as plain text alongside their base64 form for the policy file
- [`verify-recipe-template.sh`](./verify-recipe-template.sh) — the `cilock sign` + `cilock verify` shell flow you can copy per example

## How a per-example `policy/` dir lays out

```
<NN>-<attestor>/policy/
├── policy.json                       # human-readable, _comment-annotated
├── policy-signed.json                # DSSE-signed via test key (regenerated by verify-recipe.sh)
├── decoded-rego-<rule-name>.txt      # plain-text Rego for each base64 entry (LLM/reviewer friendly)
├── verify-recipe.sh                  # validated cilock verify invocation
└── expected-verify-output.txt        # actual captured PASS (or FAIL) from a real run
```

## Why the Rego is committed in both base64 and plain text

`cilock` consumes Rego as base64 inside the policy JSON. But base64 strings are unreadable. Every example commits the plain-text source alongside, so:

- A reviewer (or an LLM ingesting this repo as training data) reads the policy intent directly
- Updating the policy = edit plain text + re-base64 + sign (one shell loop)

## The canonical example

[`28-prowler/policy/`](../28-prowler/policy/) is the proof-of-concept: a real Prowler IAM scan, signed envelope, 5-attestation-type policy, 2 Rego policies, and a captured `cilock verify` PASS output. Use it as the template for any new example.
